# Architecture

The modules of this system, and the seams between them. Update this file when the shape changes. Audits compare it with reality.

Duet DAW is a native desktop digital audio workstation, written in C++, built to make collaboration between a music producer and an AI easy.

The build skeleton is in place (issue sea14w): the module targets below exist and build, the app plays audio, and the checks in `AGENTS.md` run. `duet_model` carries the Action mechanism (issue quiwf3) and the whole edit vocabulary — tracks and routing, clips, MIDI notes, mixer values and sends, built-in plugin chains, automation curves, tempo and time signature, and the transport, which is written with no undo history at all (issue 4r7nlj) and which the model keeps rolling through the engine's one-time device rebuild, so that one press of Play is enough for every caller and not only for the tests (issue sohgf4), and the meters that say what that playback is putting out — the engine builds a different graph to render an Edit than to play it, so a measured render cannot answer whether a producer hears anything, and the model can play with no audio device at all so that the question survives into CI (issue vhl9d0, ADR 0006), and the record path — record-arm, input selection, monitoring, and a take landing as one Action with its file under the project folder's `audio/` (issue nfjr5x), where the same device rebuild is got out of the way before the take rather than survived during it, because a take the rebuild interrupts cannot be asked for again without becoming two (issue di0frj), and where tests can suppress that rebuild, drive it, and time the pre-roll without waiting on the engine's four-second timer (issue 2jqmj2); `duet_persistence` carries the project folder, the DUET tree and the snapshot save (issue 1c8sjh), with schema versioning and autosave still to come. The foundation spec (issue b1j3me) defines the shape they grow into.

- **Audio engine** — playback, recording, and processing. Tracktion Engine on JUCE 9 (roadmap nodes 1hn16k, lf8tnt; proven end to end at ddp1qt). The engine owns the audio thread and rebuilds its graph from the project model automatically; no Duet code runs on the audio thread.
- **Plugin hosting** — VST3 only in milestone one, through JUCE's `AudioPluginFormat` layer and the engine's `ExternalPlugin` (`JUCE_PLUGINHOST_VST3=1`). Hosting is in-process; isolation comes from crash-safe out-of-process *scanning*, which the engine ships behind `EngineBehaviour::canScanPluginsOutOfProcess`. The format seam is the engine's public `PluginManager::pluginFormatManager` (research hvv3nn) — CLAP arrives in milestone two as a second format registered into this same seam; its design is settled at hvv3nn, its open questions (extension set, host threading contract) parked in the closing notes of 89jlz1 and 00yd6o. The milestone-one "built-in" instruments and effects are engine-shipped plugins (4OSC and sampler; EQ, compressor, reverb) surfaced through the Duet facade — no Duet-authored DSP runs in the audio callback until Duet-authored devices arrive (decision on spec b1j3me, 2026-08-17).
- **`duet_model`** — the edit vocabulary layer over the engine's `Edit`, and the engine seam: its public interface exposes zero engine or JUCE types (opaque uint64 refs, plain seconds/beats). Every project change — producer gesture or accepted Suggestion — goes through `performAction`, the only undo-transaction boundary (ADR 0004). A plugin-chain position in that vocabulary counts the producer's plugins and not the ones Duet puts on a track for its own reasons, which is also all that reads back (ADR 0007). Undo and redo run the project's `UndoManager` directly rather than `Edit::undo()`, because the engine's own undo stops a running recording first, and an undo that could end a take is what writing the transport with no undo history exists to prevent (issue nfjr5x). This module also tells the engine where a recording goes, through the one `EngineBehaviour` Duet supplies. Suggestion Audition (apply-and-revert, invisible to undo) lives here.
- **`duet_persistence`** — project folder lifecycle, snapshot save, autosave/recovery, and schema migration of the DUET tree (ADR 0005). Same engine-free facade rule, with one declared exception: a save writes the project's whole state, and the engine's state tree *is* that state, so this module — and only this module — reaches the `Edit` behind the model facade, through the `duet::model_engine_access` target and its off-the-public-path header. What goes into the DUET tree crosses that facade as a `DataNode` — a named node with named values and named nodes under it, text all the way down — so that what writes Duet's own project data needs no engine and no JUCE. The interface's per-project view state travels that way, and it travels only at one moment: a save asks for it through `onCaptureViewState` and writes it with no undo manager, which is what makes the producer's layout something an undo never puts back and something that never makes a project dirty (issue fcsez4).
- **`duet_app`** — the JUCE 9 GUI application shell: message loop, device management, transport, the app-global settings store over the engine's PropertyStorage, and the one main window `duet_gui`'s shell is the content of. It is also what knows about projects: the shell knows panels, and the host puts its project commands into the Duet menu under the shell's panel toggles and hands the open project's view to the persistence facade. Software renderer by default; per-surface `OpenGLContext` as the escape hatch. The message thread is the sole writer of the project model; analysis, thumbnails, and offline renders run on worker threads.
- **`duet_gui`** — the producer-facing interface (spec issue 535bbo): arrangement timeline, piano roll, mixer, browser, transport bar, and the Collaborator panel's styling, in a single docked main window. Depends on `duet_model` (every edit gesture ends in `performAction`) and `duet_persistence`; hosted by `duet_app`. Every surface splits into a paintless view-model (geometry, grid/snap arithmetic, hit-testing, selection, view-state serialization — the test seam) and a thin `juce::Component` that only paints and forwards events, and the split is a link error rather than a review comment: the module is two targets, `duet::gui` for the paintless half, which links no JUCE at all and is what `duet_tests` links, and `duet::gui_components` for the components, which is where JUCE arrives (issue xxv9ng). The first slice carries the Graphite visual language — one token set with both palettes, the eight track colours, the Collaborator's reserved teal, and Inter compiled into the binary — plus the appearance (theme resolution against the desktop, and the interface scale that turns a logical unit into pixels) and the Settings window it is set from. The second carries the main window itself (issue fcsez4): `MainShell` — the transport strip, the arrangement, the browser and Collaborator docks, their draggable dividers, the collapsible bottom panel with its Piano Roll and Mixer tabs, and the one Duet menu that stands in for a menu bar — over three paintless pieces it reads. `ViewState` is the per-project view: what the docks are and where, the zoom and scroll, a row per track. It lives in a VIEW child of the DUET tree, and the shell writes every layout gesture into it rather than around it, which is what makes the layout the project's. `Shortcuts` is the keyboard policy, and the reason it is a policy and not a switch inside a component: a key held with no Ctrl and no Alt is a bare key, and a bare key is the producer typing whenever a text field has the focus — later surfaces register their own keys with the same table. The third slice fills the arrangement in (issue 5he6vd): `TimelineGeometry` is the time↔pixel mapping, the adaptive grid — the finest subdivision whose lines are 18 px apart — and pointer-anchored zoom, and it keeps no zoom or scroll of its own, because the view state is where those live and what a save captures; `ArrangementView` is the surface over it, holding the scroll and zoom conventions every surface shares and where the playhead is; `ArrangementCanvas` paints both and forwards the producer's gestures, and it is the first surface that is not an empty dock. What the timeline is drawn against is one seam, `TimelineClock` — the project's metre, its length, and its transport, in beats — so a surface outlives the project open in it and a repaint reads values the engine has already published rather than taking a lock. `SessionClock` is that seam over the model, and `duet_app` hands one to the shell as it opens a project. `WindowGeometry` and `Rendering` are the two app-global answers the shell needs — where the window opens, whichever project opens in it, and whether a surface is on the software renderer or through `AcceleratedSurface`'s `OpenGLContext`. App-global UI settings live behind `duet::gui::Settings`, which `duet_app` implements over the engine's PropertyStorage.
- **AI integration** — decided (spec issue js437t; ADRs 0002, 0003), and the seam itself is built (issue d7h5f5). Three parts, one seam:
  - The **Collaborator service**, `duet_collab`: socket server, Task Run lifecycle, tool dispatch, the deterministic analysis layer with its per-track cache, the Suggestion manager, and the estimate ledger. The transport half exists — a Unix domain socket the DAW listens on, newline-delimited JSON-RPC 2.0 in both directions over the one connection it accepts, and the sidecar owned as a child process, spawned by the first question asked of it, replaced when found dead, and killed with the DAW. The module links no engine, no JUCE and nothing graphical, which is what makes the real-time rule below structural rather than a promise; `nlohmann/json` (MIT) is its one dependency, the socket and the child process being POSIX calls. JUCE has no Unix domain socket to use instead — `StreamingSocket` is TCP and `NamedPipe` is a pair of FIFOs — and the protocol's socket *path* is what the sidecar is launched with and what proves at exit that nothing was left behind.
  - The **sidecar**, a minimal Node host embedding pi's SDK, bundled as a standalone binary: agent loop, provider auth, model switching, streaming.
  - The **socket protocol** between them — newline-delimited JSON-RPC 2.0 over a local socket; the DAW is the server and spawns the sidecar. Every prompt, streamed event, cancellation, and tool call crosses this seam, and its contracts are transport-independent, so a native C++ loop can replace the sidecar without contract changes.
  Real-time rule: nothing on the AI side touches the audio thread — the socket has its own thread, project-model reads marshal onto the message thread, analysis renders on worker threads.
  The service is verified through the protocol itself, against a test-double sidecar (`tests/sidecar_double`) that speaks it and shares no code with the service. That double is the harness every later protocol slice reuses, and the escape hatch made concrete: anything that speaks the protocol can take the sidecar's place.
- **Build system** — settled (roadmap node psmj4y; details in spec b1j3me): CMake ≥ 3.22, Ninja Multi-Config presets, C++20 set by hand on every Duet target, FetchContent with full-SHA pins (JUCE 9 declared before Tracktion), Catch2 v3 tests, GitHub Actions CI on pinned ubuntu-24.04 with a `checks-pass` gate.
