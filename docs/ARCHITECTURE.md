# Architecture

The modules of this system, and the seams between them. Update this file when the shape changes. Audits compare it with reality.

Duet DAW is a native desktop digital audio workstation, written in C++, built to make collaboration between a music producer and an AI easy.

The build skeleton is in place (issue sea14w): the module targets below exist and build, the app plays audio, and the checks in `AGENTS.md` run. `duet_model` carries the Action mechanism (issue quiwf3) and the whole edit vocabulary — tracks and routing, clips, MIDI notes, mixer values and sends, built-in plugin chains, automation curves, tempo and time signature, and the transport, including its no-undo loop and metronome state and its lock-free published CPU load, which is written with no undo history at all (issues 4r7nlj, 1fumn6) and which the model keeps rolling through the engine's one-time device rebuild, so that one press of Play is enough for every caller and not only for the tests (issue sohgf4), and the meters that say what that playback is putting out — the engine builds a different graph to render an Edit than to play it, so a measured render cannot answer whether a producer hears anything, and the model can play with no audio device at all so that the question survives into CI (issue vhl9d0, ADR 0006), and the record path — record-arm, input selection, monitoring, and a take landing as one Action with its file under the project folder's `audio/` (issue nfjr5x), where the same device rebuild is got out of the way before the take rather than survived during it, because a take the rebuild interrupts cannot be asked for again without becoming two (issue di0frj), and where tests can suppress that rebuild, drive it, and time the pre-roll without waiting on the engine's four-second timer (issue 2jqmj2); `duet_persistence` carries the project folder, the DUET tree and the snapshot save (issue 1c8sjh), plus its integer schema, oldest-first in-memory migration chain, and refusal result for a file from a newer Duet (issue ne2fhn), and autosave/crash recovery: a dirty project writes one atomic recovery snapshot beside the project file on the app-global off/2/5/10-minute interval, and a newer snapshot is offered on open (issue 3vwusn). The foundation spec (issue b1j3me) defines the shape they grow into.

- **Audio engine** — playback, recording, and processing. Tracktion Engine on JUCE 9 (roadmap nodes 1hn16k, lf8tnt; proven end to end at ddp1qt). The engine owns the audio thread and rebuilds its graph from the project model automatically; no Duet code runs on the audio thread.
- **Plugin hosting** — VST3 only in milestone one, through JUCE's `AudioPluginFormat` layer and the engine's `ExternalPlugin` (`JUCE_PLUGINHOST_VST3=1`). Hosting is in-process; isolation comes from crash-safe out-of-process *scanning*, which the engine ships behind `EngineBehaviour::canScanPluginsOutOfProcess`. The format seam is the engine's public `PluginManager::pluginFormatManager` (research hvv3nn) — CLAP arrives in milestone two as a second format registered into this same seam; its design is settled at hvv3nn, its open questions (extension set, host threading contract) parked in the closing notes of 89jlz1 and 00yd6o. The milestone-one "built-in" instruments and effects are engine-shipped plugins (4OSC and sampler; EQ, compressor, reverb) surfaced through the Duet facade — no Duet-authored DSP runs in the audio callback until Duet-authored devices arrive (decision on spec b1j3me, 2026-08-17).
- **`duet_model`** — the edit vocabulary layer over the engine's `Edit`, and the engine seam: its public interface exposes zero engine or JUCE types (opaque uint64 refs, plain seconds/beats). Every project change — producer gesture or accepted Suggestion — goes through `performAction`, the only undo-transaction boundary (ADR 0004). A plugin-chain position in that vocabulary counts the producer's plugins and not the ones Duet puts on a track for its own reasons, which is also all that reads back (ADR 0007); scanned VST3s enter that same chain and their normalised parameters enter the same Action/undo path as built-ins. The app-global known list and bad-file list are the reads around the engine's out-of-process scanner. A second, component-only engine crossing hosts a VST3's native editor without putting engine or JUCE types into this facade (ADR 0008); every gesture from that editor returns through the same Action vocabulary. Undo and redo run the project's `UndoManager` directly rather than `Edit::undo()`, because the engine's own undo stops a running recording first, and an undo that could end a take is what writing the transport with no undo history exists to prevent (issue nfjr5x). This module also tells the engine where a recording goes and that scans use a child process, through the one `EngineBehaviour` Duet supplies. It owns the app-global settings store as well, because that store is the engine's own `PropertyStorage` and its `Settings.xml` holds the interface's settings beside the engine's: one store is open at a time, every Engine a session makes is lent it through a forwarding adapter, and `duet::model::AppSettings` is what a holder outside the engine — the shell's `duet::gui::Settings` — reaches it through, string in and string out (issue uztxbx). The arrangement's named sections and the key a project declares are Duet's own state on the Edit's own tree, because the engine's `ArrangerTrack` would be a whole track carrying three strings. Offline rendering lives here too: the whole project or one track on its own, at a shape fixed in the model rather than taken from an audio device, and callable from a worker thread — which is where the thread model puts a render and what the Collaborator's measured analysis calls (ADR 0006). That shape is public, because what measures a render needs it, and the block it names is also how early a rendered sound may begin. Each of those two has a detached twin, which renders a copy of the project rather than the project, because an Edit that is rendering is an Edit that is not playing: a render nobody asked to wait for — a measurement while the producer works — goes through the twin and costs the producer no gap, and a render they are waiting on still takes the transport with it, the model's play retry now waiting a render out rather than spending its window on one (issue xbh9qk). A render is asked between its blocks whether it is still wanted, so one nobody is waiting for stops rather than finishes; `readAudioFile` reads what it wrote back as plain samples, this being the only module that can open an audio file; and `trackStateDigest` says when what one track renders has changed, which is what a measured analysis is cached against — an edit to another track leaves it where it was. Suggestion Audition lives here: an engine-free flat operation list is materialized against a reusable detached Edit, then its state is applied to and reverted from the real Edit with no UndoManager; engine bookkeeping writes raised by that state change are isolated and removed, so producer undo and redo remain untouched. One such list appends onto another with its placeholders renumbered, so that neither list can resolve the other's creations and any set of independently applicable Elements is still one Action.
- **`duet_persistence`** — project folder lifecycle, snapshot save, autosave/recovery, and schema migration of the DUET tree (ADR 0005). Same engine-free facade rule, with one declared exception: a save writes the project's whole state, and the engine's state tree *is* that state, so this module — and only this module — reaches the `Edit` behind the model facade, through the `duet::model_engine_access` target and its off-the-public-path header. What goes into the DUET tree crosses that facade as a `DataNode` — a named node with named values and named nodes under it, text all the way down — so that what writes Duet's own project data needs no engine and no JUCE. The interface's per-project view state travels that way, and it travels only at one moment: a save asks for it through `onCaptureViewState` and writes it with no undo manager, which is what makes the producer's layout something an undo never puts back and something that never makes a project dirty (issue fcsez4). Explicit save and autosave both pass through the same snapshot writer, which captures a hosted VST3's opaque state on the copy as well as explicit parameter values; autosave targets the one recovery file instead of the project file, and explicit save removes recovery. Save As snapshots the current state into a recursive copy of the project folder and returns a project opened on that copy, leaving the source folder untouched.
- **`duet_app`** — the JUCE 9 GUI application shell: message loop, device management, transport, the app-global settings store over the engine's PropertyStorage (stamped with the running application version at startup), and the one main window `duet_gui`'s shell is the content of. That store is paintless and lives in `duet_app_core` beside the lifecycle, so what the tests link is the one the shell runs on; it holds the model's single app-global store rather than opening a `PropertiesFile` of its own (issue uztxbx). It is also what knows about projects: its paintless `ProjectLifecycle` owns the always-open project, reopens the last viable folder or numbers a real `Untitled N` folder, seeds the instrument-and-audio-track starting state, applies Save / Discard / Cancel policy, and maintains Recent; the JUCE host supplies the dialogs and puts New, Open, Save, Save As and Recent into the Duet menu under the shell's panel toggles. The host hands the open project's view to the persistence facade and reconnects the shell whenever the lifecycle replaces a project. Software renderer by default; per-surface `OpenGLContext` as the escape hatch. The message thread is the sole writer of the project model; analysis, thumbnails, and offline renders run on worker threads.
- **`duet_gui`** — the producer-facing interface (spec issue 535bbo): arrangement timeline, piano roll, mixer, browser, transport bar, and the Collaborator panel's styling, in a single docked main window. Depends on `duet_model` (every edit gesture ends in `performAction`) and `duet_persistence`; hosted by `duet_app`. Every surface splits into a paintless view-model (geometry, grid/snap arithmetic, hit-testing, selection, view-state serialization — the test seam) and a thin `juce::Component` that only paints and forwards events, and the split is a link error rather than a review comment: the module is two targets, `duet::gui` for the paintless half, which links no JUCE at all and is what `duet_tests` links, and `duet::gui_components` for the components, which is where JUCE arrives (issue xxv9ng). The first slice carries the Graphite visual language — one token set with both palettes, the eight track colours, the Collaborator's reserved teal, and Inter compiled into the binary — plus the appearance (theme resolution against the desktop, and the interface scale that turns a logical unit into pixels) and the Settings window it is set from. The second carries the main window itself (issue fcsez4): `MainShell` — the transport strip, the arrangement, the browser and Collaborator docks, their draggable dividers, the collapsible bottom panel with its Piano Roll and Mixer tabs, and the one Duet menu that stands in for a menu bar — over three paintless pieces it reads. `ViewState` is the per-project view: what the docks are and where, the zoom and scroll, a row per track. It lives in a VIEW child of the DUET tree, and the shell writes every layout gesture into it rather than around it, which is what makes the layout the project's. `Shortcuts` is the keyboard policy, and the reason it is a policy and not a switch inside a component: a key held with no Ctrl and no Alt is a bare key, and a bare key is the producer typing whenever a text field has the focus — later surfaces register their own keys with the same table. The third slice fills the arrangement in (issue 5he6vd): `TimelineGeometry` is the time↔pixel mapping, the adaptive grid — the finest subdivision whose lines are 18 px apart — and pointer-anchored zoom, and it keeps no zoom or scroll of its own, because the view state is where those live and what a save captures; `ArrangementView` is the surface over it, holding the scroll and zoom conventions every surface shares and where the playhead is; `ArrangementCanvas` paints both and forwards the producer's gestures, and it is the first surface that is not an empty dock. `TransportBar` is the paintless state and gesture seam for the live strip above it: fixed-width musical and wall-time readouts, tempo and metre Actions, transport/history controls, project dirty status, and CPU health; the strip samples only the model's published load. Its grid choice and follow-playhead toggle live with the project's `ViewState`, so the arrangement reads the same choice for drawing, snap, and playback following. The Mixer is the paintless state and gesture seam for ordered track strips plus the specialised Master, transient fader/pan gestures, cycle-safe routing, insert chains, and visible-range peak hold; its component samples published meters at 30 Hz and paints only cached scalars. Plugin editors are the only floating windows: native VST3 when available and generic otherwise, one per plugin, with bypass and the app-global Duet preset library in their chrome. What the timeline is drawn against is one seam, `TimelineClock` — the project's metre, its length, and its transport, in beats — so a surface outlives the project open in it and a repaint reads values the engine has already published rather than taking a lock. `SessionClock` is that seam over the model, and `duet_app` hands one to the shell as it opens a project. `WindowGeometry` and `Rendering` are the two app-global answers the shell needs — where the window opens, whichever project opens in it, and whether a surface is on the software renderer or through `AcceleratedSurface`'s `OpenGLContext`. App-global UI settings live behind `duet::gui::Settings`, which `duet_app` implements over the engine's PropertyStorage; the Interface tab includes the directory used only for later projects and the off/2/5/10-minute autosave choice, defaulting to ten minutes. The right dock is the surface the Collaborator speaks from (issue 4jipx2): `CollaboratorPanel` is the paintless half — the conversation of producer messages and Collaborator commentary, the composer beneath it, the quick prompts that change with the selection, the context chip frozen onto a message at the moment it is sent, and the Task Run card's running state with its rotating status phrases — and `CollaboratorPanelCanvas` is the one place in the interface the reserved teal and the ✦ badge are drawn, which a test over the module sources is what keeps true. The panel reads and styles only: it performs no Action and never reads the project, asking the shell for the one current selection instead. What answers the producer is behind `CollaboratorPanel::Source`, and until spec js437t's service exists that is `ScriptedCollaborator`, a development-only stand-in with no AI backend, no socket and no network, through which a Task Run, a cancellation and a failure are each reachable by hand. Automation hangs under the arrangement (issue 3rd6lu): `AutomationLanes` is the paintless seam for the area a track header opens beneath its row — the lanes in it, each bound to a curve chosen from its own picker (the track's volume or pan, or a parameter of one of its plugins) and drawn against that target's own value range, the geometry that says what a height in a lane is worth, and the double-click, drag and right-click that each end in one named Action. It draws on the arrangement's own `TimelineGeometry`, so a curve and the clips above it share one grid, zoom and scroll, and which lanes a track has open is view state, kept in its `TRACKVIEW` row and captured by a save. Segments are straight in milestone one and the path from the gesture to the model says so rather than assuming it: `duet::model::AutomationPoint` carries its own curvature, which every gesture returns to the model untouched.
- **AI integration** — decided (spec issue js437t; ADRs 0002, 0003), and the seam itself is built (issues d7h5f5, xy9438). Three parts, one seam:
  - The **Collaborator service**, `duet_collab`: socket server, Task Run lifecycle, tool dispatch, the deterministic analysis layer with its per-track cache, the Suggestion manager, and the estimate ledger. The transport half exists — a Unix domain socket the DAW listens on, newline-delimited JSON-RPC 2.0 in both directions over the one connection it accepts, and the sidecar owned as a child process, spawned by the first question asked of it, replaced when found dead, and killed with the DAW. The module links no engine, no JUCE and nothing graphical, which is what makes the real-time rule below structural rather than a promise; `nlohmann/json` (MIT) is its one dependency, the socket and the child process being POSIX calls. JUCE has no Unix domain socket to use instead — `StreamingSocket` is TCP and `NamedPipe` is a pair of FIFOs — and the protocol's socket *path* is what the sidecar is launched with and what proves at exit that nothing was left behind. The Task Run lifecycle sits on that transport (issue xy9438): `startRun` takes the prompt and the opening context — what the producer had selected, where the playhead was, whether the transport was rolling — and returns at once, having handed the run to the service thread rather than waited on a sidecar; what comes back is a `TaskRunListener`'s calls, which are the whole of what the DAW learns about a run. One run at a time, and whether the service holds an active run *is* that rule: a second `startRun` is refused with `runAlreadyActive` and the run in progress never notices. A run ends exactly once, and the id that names it is cleared under the same lock that reads it, so every event afterwards — a late ending, an unknown run, words after the last word — is ignored by construction rather than by a second guard. Cancellation is client-side: the run ends canceled here and `run.cancel` goes on to stop the work, so a producer never waits on a backend to stop asking it something. Everything that fails, fails fast and clears: a refused `run.start`, a sidecar that died mid-run, one that never started at all. Nothing queues and nothing retries — the next run is the producer's to ask for, and it is what spawns the replacement sidecar. Tool dispatch sits beside it (issue v5yhh1): a `ToolRegistry` is the closed set the vocabulary is, and a name outside it is answered `unknownTool` rather than with silence or a guess, on a connection the refusal never disturbs. What answers the five project-read tools is a second target, `duet::collab_tools` — the same split `duet_gui` makes, and for a harder reason: the service above must link no engine, and reading the project means linking the model, which links the engine. So `ProjectTools` holds the model and the service holds the socket, and the only things crossing between them are JSON and one function that puts a read on the message thread. That function is the whole of the real-time rule for a tool: a read runs where the project model's sole writer runs, the service thread marshals and waits, and the authoritative state is what is read rather than a copy kept in step with it. Every value in a result is a bare scalar, because everything read from the project model is by construction a fact (ADR 0002); the one wrapped value the contract names is a scanned plugin's own display text, whose meaning is the plugin's and not Duet's. Buses are tracks here: the master is `track-master` and every group is itself, in the track list and wherever a track id is taken. A result states its stable content first and the content an edit moves last — the seam's JSON keeps the order it was written in, which is what makes a fader change invalidate the tail of a cached tool result rather than its middle — and the same project state produces the same bytes however long apart two calls are. Measured analysis is the third piece and a third target (issue 3bgymu): `duet::collab_analysis` is the tier-2 DSP as pure functions of a waveform — peak and true peak, RMS and crest factor, integrated and short-term loudness per ITU-R BS.1770, the energy in seven fixed named bands, the spectral centroid and flatness, stereo correlation and width, onsets by spectral flux, and monophonic f0 by YIN — and it links nothing at all, not the engine, not JUCE, not even the JSON the seam speaks, which is both what keeps it away from the audio callback and what makes the spec's second test seam a plain function call over a signal built by hand. `TrackAnalysis` in `duet::collab_tools` is the tool over it: it answers `get_track_analysis` from the track's rendered output, keeping that render per track and keyed on that track's own edit state, so the first call on a track costs a render and the ones after it do not, an edit to the track throws it away, and an edit to another track does not. Rendering and measuring both happen on the service thread, the project being read on the message thread and nowhere else, so a producer keeps editing while a first call is in flight; the run is asked whether it is still wanted before the render, between its blocks and between the routines, so a cancel is not something anyone waits out. Playing and recording survive a measurement too, because the render is not of the project: an offline render puts the Edit it renders into the engine's render status and stops that Edit's transport for as long as it runs (engine notes), so the tool renders a detached copy of the project instead and the project is never in render status at all (issue xbh9qk). A bar range narrows what is measured, first bar and last and both included, while onsets are found over the whole render and then read for the part that was asked about, since a note held across the start of a range did not begin there. Everything it answers with is a bare scalar, and the band edges it tells the model are the ones the routine measures — the sidecar's own description of the tool, held to the routine's table by a test. Estimated content is the layer above it (issue 2z0y5u), and everything in it is a guess that says so. `analysis::estimatedKey` and `estimatedChord` read a pitch-class profile off the same transform the bands are read off and score it — the Krumhansl-Schmuckler key profiles for the one, major and minor triad templates for the other — so what comes back is a name and how well the notes fit it. `ContentEstimates` in `duet::collab_tools` answers `estimate_audio_content` out of that: the key of the stretch asked about, and the chord in each of its bars, read from the same `TrackRenders` the measurement reads, which is what makes a track measured and estimated in one run cost one render between them. Nothing it answers with is bare, and what it cannot read it does not answer — a silent track has no key, and an aspect nobody asked for is absent rather than empty, which is also how the two aspects the transcription model will bring (issue bmrxnw) stay out of the model's reach until they can be answered. The wrapper is `Estimate` — the value, `source: "estimated"`, the routine that made it, and a confidence from 0 to 1 — and wrapping is not a separate act from recording: `EstimateLedger::record` is what answers with the wrapped value, so nothing can hand an estimate over without the run's ledger holding it. That ledger is what marks a run, and the service reads it rather than anything the model says about itself: once a run has been handed one estimate, every piece of commentary it sends afterwards carries the mark, used or unused, mentioned or not — over-marking being the accepted cost of never under-marking. A run's ledger is emptied when the run begins, so nothing is inherited from the run before it however that one ended, and it outlives the run, because the mark on what was said is inspectable for as long as the conversation holds it. The one write-tool sits in that same target (issue cwz0of): `SuggestTool` answers `suggest`, the closed Edit Vocabulary mirroring what the milestone-one interface can do and nothing else — no operation in it brings audio into being, an audio clip being something the Collaborator may move, trim, loop, duplicate and delete and never create. A call is a summary and an ordered list of elements, and an element is the cherry-pick unit, so an operation may name what an earlier operation of *its own* element makes — written `#name`, which no project id can be — and never what another element makes, because an element the producer cannot accept by itself is not an element. Checking and building are one walk over the call, on the message thread with the rest of the tools: every id is resolved against the live project and every value held inside the range the thing it is written to has, so a refusal names the position it happened at and what was wrong there, and a run corrects and calls again. Nothing exists until all of it checks out, and what then exists is data: the project state, its file and the producer's undo history are exactly as the call found them, and a Task Run makes at most one Suggestion. What is kept is the model's own applicable form — one operation list per element, named for the element, and one for the whole, named for the summary — which is what the Suggestion manager cherry-picks from and what Audition applies. The Suggestion manager is the layer over it (issue aw5t9l), and it is what makes a Suggestion a conversation rather than a patch. It holds every Suggestion of an app session, each pending until the producer resolves it, and the request behind each, because a revision and a redo against current state are that same request asked again; several are pending at once and independently. Accepting an Element applies exactly that Element's operations as one Action named for the Element, accepting what is left of a Suggestion applies those as one Action named for the summary — the model's own lists appended into one, placeholders renumbered, which is the whole of what cherry-pick is at that seam — and rejecting applies nothing. A Suggestion ends when no Element of it is pending, accepted if any Element was and rejected if none was, and an ending is final: nothing resolves a Suggestion twice. Staleness is measured and not reported: every id a pending Suggestion's operations name is remembered as what the project said about it when the Suggestion was made, and a Suggestion the project has since said something else about is stale, which leaves it auditionable and acceptable and takes away only its claim to still fit. So a change the producer undoes takes the staleness with it, a Suggestion's own accepted Element is not the project moving out from under it, and another Suggestion's acceptance is. Auditioning belongs to the manager too, and there is one at a time: what it hands the model is whatever the Suggestion has left to accept, so a producer hears what accepting it now would do, and a live Audition is the project holding a Suggestion's own changes rather than the producer's, which is why nothing is measured for staleness while one lasts. Replying supersedes a pending Suggestion and leaves a rejected one rejected, and either way starts one run carrying the original request and what the producer typed; redoing supersedes and carries the original request and every named thing that has changed under it, what it was and what it is now — request first and changes last, which is the prompt-cache discipline the spec asks of everything this side sends. None of it is written down: the Suggestions, the requests behind them and the replies to them live in that one object for the app session, and a save while one is pending writes a file that knows nothing about it.
  - The **sidecar**, `sidecar/`: pi's agent loop wearing Duet's prompt, built by bun into one standalone binary that ships beside the application (issue oocnng). It is `@earendil-works/pi-agent-core` and `@earendil-works/pi-ai` and deliberately not `@earendil-works/pi-coding-agent` — the loop, the provider abstraction, the auth and the streaming are worth having and a coding agent's tools and identity are not (measured at d8k46e). The agent is built with an empty built-in tool set, so the only tools that exist are the eight in `src/vocabulary.ts` — the seven of the Tool Vocabulary and the one write-tool — and each of them has one body: ask the DAW across the socket and hand back what it says. A refusal is thrown rather than returned, because pi's loop turns a throw into an error tool result the model can correct against, which is what an unknown id in a `suggest` call and a tool this DAW does not answer yet both need. The system prompt is Duet's own and is in two halves: `collaboratorPrompt` — the Collaborator's identity, that it never hears audio, that a bare tool value is a fact and a wrapped one a guess, when to hedge, what a Suggestion is and what an Element must be, and how it talks — never moves, and whatever `configure` sends in `systemPromptParams` is rendered after it, which is the prompt-cache discipline stated as a shape rather than as a rule to remember. One session lives as long as the process, so each Task Run is another turn of one conversation and a provider's cache has a prefix worth keeping. The binary is silent by construction: it shares the DAW's stdout and stderr, so nothing is written to either and even a crash goes quietly, with `DUET_SIDECAR_DEBUG` the developer's way in. Two arguments exist only for testing — `--dump-prompt` writes the assembled prompt and tool list, and `--offline-script` puts a scripted model where the provider would be, which is the mirror of `tests/sidecar_double`: the double lets the DAW be driven with no sidecar, and the script lets the sidecar be driven with no provider, so every rule of the seam is asserted by something that shares no code with what it is asserting about. `tests/SidecarTests.cpp` is that suite, and it skips itself on a machine with no bun to build the binary with; CMake's `DUET_SIDECAR_ENABLED` is the same switch said deliberately. Provider auth, the model list and the picker are not here yet (issue i84fbb); until they are, credentials are whatever pi resolves from the environment.
  - The **socket protocol** between them — newline-delimited JSON-RPC 2.0 over a local socket; the DAW is the server and spawns the sidecar. Every prompt, streamed event, cancellation, and tool call crosses this seam, and its contracts are transport-independent, so a native C++ loop can replace the sidecar without contract changes.
  Real-time rule: nothing on the AI side touches the audio thread — the socket has its own thread, project-model reads marshal onto the message thread, analysis renders on worker threads.
  The service is verified through the protocol itself, against a test-double sidecar (`tests/sidecar_double`) that speaks it and shares no code with the service. That double is the harness every later protocol slice reuses, and the escape hatch made concrete: anything that speaks the protocol can take the sidecar's place. The tools are verified the same way and against the same double, over a real socket and against a real project: `tests/fixtures/collaborator` is the fod077 corpus rebuilt as seven real Duet projects, and each file is both the recipe the suite builds and the expectation it asserts.
- **`duet_realtime`** — the audio-callback seam: one header carrying `DUET_NONBLOCKING`, the feature-tested annotation an entry point wears, and the target that carries `-fsanitize=realtime` in the `linux-rtsan` configuration and nowhere else. The two travel together because they are the same decision — the annotation is where RealtimeSanitizer starts watching, and the flag is what makes it watch — so a Duet target holding callback code links `duet::realtime`, and that link is what puts it under the sanitizer. What the nightly reaches is therefore the build graph rather than a list in a preset, and `git grep duet::realtime` is the list. Milestone one has no Duet-authored DSP — its instruments and effects are the engine's, surfaced through the facade — so what the nightly runs is a probe at each seam under `tests/rt_probes`: one `tracktion::engine::Plugin` entered at `applyToBuffer` and one `juce::AudioProcessor` entered at `processBlock`, the latter built as a VST3 because that is the only way the engine hosts one, both driven by offline render with no audio device (ADR 0006, issue uaqfnv).
- **Build system** — settled (roadmap node psmj4y; details in spec b1j3me): CMake ≥ 3.22, Ninja Multi-Config presets, C++20 set by hand on every Duet target, FetchContent with full-SHA pins (JUCE 9 declared before Tracktion), Catch2 v3 tests, GitHub Actions CI on pinned ubuntu-24.04 with a `checks-pass` gate.
