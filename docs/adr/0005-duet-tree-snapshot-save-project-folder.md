# 0005 — Duet data in a DUET tree, snapshot save, project as a folder

Context: Duet needs its own durable project data next to the engine's, and the engine's save path (`flushState`) writes parameter blobs through the UndoManager — polluting undo history and clearing the redo stack exactly when automation has diverged a parameter. Decision: Duet's data lives in a DUET child tree under `edit.state` carrying `duetSchemaVersion` (migrations oldest-first on load, newer-than-app files refused); saving copies `edit.state`, applies the parameter blobs to the copy with no UndoManager, and writes the copy; a project is a folder (edit file plus `audio/`, project-relative paths). Reason: one file with atomic save and automatic persistence, a save that is provably undo/redo-neutral, and self-contained portable projects; proven in the `prototype/duet-persistence` spike (roadmap node rquzdc).
