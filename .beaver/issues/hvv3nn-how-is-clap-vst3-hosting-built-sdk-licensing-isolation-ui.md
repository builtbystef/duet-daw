Research session. Milestone one hosts CLAP and VST3 plugins (node kimula). With the application foundation chosen (node 1hn16k — JUCE vs Qt changes the answer materially), settle how hosting is built:

- SDK licensing: the VST3 SDK's GPLv3/proprietary dual license, and how it interacts with the chosen foundation's license and the product's licensing plans; CLAP's MIT license.
- Hosting architecture: in-process vs out-of-process (crash isolation), plugin scanning, plugin state save/restore.
- Plugin UI embedding on Linux (X11/Wayland) and Windows — the platforms that ship first.
- Sidechain routing into plugins, since sidechaining is a milestone-one requirement (node kimula).

Primary sources: official SDK docs and licenses, not recall. Deliverable: a recommendation with cited trade-offs, ready to become an ADR.

## Question

How is CLAP + VST3 hosting built? The brief's licensing sub-question was already answered at node 1hn16k (the VST3 SDK is now MIT), so this session covers: in-process vs out-of-process, plugin scanning, state save/restore, GUI embedding on Linux and Windows, sidechain routing — and how much of a CLAP host to write for milestone one.

## Answer

**Host both formats through one seam: implement CLAP as a `juce::AudioPluginFormat` + `juce::AudioPluginInstance` pair and register it into Tracktion's public `PluginManager::pluginFormatManager`.** Everything downstream then treats CLAP exactly like VST3, because Tracktion's `ExternalPlugin` talks only generic `juce::AudioProcessor` API — no format-specific calls in the hot paths. This is not a guess about an untested seam: Tracktion already ships a non-JUCE format through it (the Cmajor patch format, registered two lines after `addDefaultFormatsToManager`).

The consequences, in order of how much work each saves or costs:

- **Sidechain, state, automation, bus layout, editor windows, programs, latency, undo and Edit persistence all come free** — but only via this route, and only if the CLAP wrapper exposes its sidechain as a second JUCE input *bus*. Tracktion never asks "is this bus a sidechain"; `canSidechain()` is a pure channel-count test.
- **Hosting is in-process.** Neither JUCE nor Tracktion Engine has any out-of-process hosting facility, and the only permissively-licensed reference doesn't exist — Carla, the one open implementation, is GPL-2.0-or-later and already out of scope. Building it means shared-memory audio transport plus a blocking semaphore round-trip inside every audio callback, per bridged plugin.
- **Scanning is out-of-process, and that is the isolation that actually matters.** Tracktion already ships the complete child-process scanner (coordinator, worker, crash detection, one-retry recovery, Windows SEH wrapping); it is off by default behind one `EngineBehaviour` override. Two small patches are needed to make it cover CLAP.
- **Linux is X11 only, for the whole application.** JUCE 9 has no Wayland peer, and CLAP's own header says Wayland embedding "is currently not supported, use floating windows". Duet runs under XWayland. This is a platform fact, not a plugin fact.
- **The CLAP host itself is the real cost of milestone one.** No usable CLAP hosting library exists at any license. The only `juce::AudioPluginFormat` implementation of CLAP is MIT but dead (last commit 2022-10-06, 13 stars, self-described "super-alpha", with MIDI, state, GUI, latency and thread-check unimplemented) — a reference, not a dependency.

## Findings

### 1. Tracktion Engine has no CLAP, and the premise that Waveform does could not be confirmed

- A case-insensitive grep for `clap` across tracktion_engine @ 494e91d2 returns three files, none of them hosting code: two `BinaryData` entries for a hand-clap audio sample, and `project/dawproject/tracktion_DAWprojectMapping.h:75` — `static constexpr auto ClapPlugin = "ClapPlugin";`, a string constant in the DAWproject interchange element table, referenced nowhere else in the module.
- `FEATURES.md:61` — "External plugin formats supported by JUCE". `.gitmodules` declares one submodule, JUCE `develop`. `modules/3rd_party/` vendors no CLAP.
- JUCE 9 has no CLAP either: `format_types/` holds only AudioUnit, LADSPA, LV2, VST3, VST, and `juce::addDefaultFormatsToManager` (`juce_AudioPluginFormatManagerHelpers.cpp:38-59`) adds exactly those. CLAP appears in JUCE's Q3 2025 roadmap post for authoring, not hosting.
- **The brief's premise that Waveform supports CLAP is unconfirmed and the available evidence points the other way.** CLAP's own host list at cleveraudio.org/hosts-and-plug-ins/ (fetched 2026-08-07) names "Anklang, Bitwig Studio, Carla, Cockos Reaper, EXT64, FL Studio, Metro, MultitrackStudio, MuLab, Plogue Bidule, Studio One, Qtractor, Zrythm" — Waveform is absent. tracktion.com's Waveform "What's New" page does not mention CLAP. GitHub issue search on Tracktion/tracktion_engine for "clap" returns 0 results. So there is no closed-Waveform CLAP implementation to hope for, and no reason to wait for one.

### 2. The seam: a custom `juce::AudioPluginFormat`, with in-tree precedent

- `ExternalPlugin` doc, `plugins/external/tracktion_ExternalPlugin.h:22` — "Wraps a juce::AudioPluginInstance (VST2, VST3, AU, etc.) as a tracktion Plugin."
- **Precedent, `plugins/tracktion_PluginManager.cpp:74-77`:** `juce::addDefaultFormatsToManager (pluginFormatManager);` then `if (auto patchFormat = createCmajorPatchPluginFormat (engine)) pluginFormatManager.addFormat (std::move (patchFormat));`. Cmajor is not a JUCE-built-in format, it is registered by Tracktion through the same public seam Duet would use. `pluginFormatManager` is a public member (`tracktion_PluginManager.h:47`).
- A second, more surgical seam exists: `PluginManager::createPluginInstance`, a public `std::function<std::unique_ptr<juce::AudioPluginInstance>(const juce::PluginDescription&, double, int, juce::String&)>` documented at `tracktion_PluginManager.h:95-103` — "By default this simply uses the PluginManager's pluginFormatManager but it can be set to provide custom behaviour." `ExternalPlugin` calls it at `tracktion_ExternalPlugin.cpp:1880`.
- **`ExternalPlugin` is format-agnostic in every path that matters**, all `tracktion_ExternalPlugin.cpp`: state `pi->getStateInformation` :1060 / `setStateInformation` :1126; buses `getBusCount`/`setBusesLayout` :401-432, :1540-1544, :1773-1789; programs :1638-1727; latency `pi->getLatencySamples()` :80-86, :1195; editor :2067-2154; parameters `pi->getParameters()` :759.
- **The rejected alternative — subclassing `tracktion::engine::Plugin` directly** and dispatching from `EngineBehaviour::createCustomPlugin` (`tracktion_EngineBehaviour.h:48-49`, "called if the PluginManager doesn't know how to create a Plugin for the given info") — needs only six pure virtuals (`tracktion_Plugin.h:174,177,227,242,263,347`) but forfeits everything in the bullet above: parameter/automation binding, state persistence, bus layout persistence, programs, latency, editor hosting, and KnownPluginList integration all become hand-written. `createCustomPlugin` is documented as a fallback for plugin *types*, not as a format seam.

### 3. What the CLAP wrapper must implement

- `juce::AudioPluginFormat` pure virtuals (JUCE 9 — note these classes moved to the **`juce_audio_processors_headless`** module), `format/juce_AudioPluginFormat.h`: `getName` :56, `findAllTypesForFile` :67, `fileMightContainThisPluginType` :104, `getNameOfPluginFromIdentifier` :107, `pluginNeedsRescanning` :110, `doesPluginStillExist` :116, `canScanForPlugins` :119, `isTrivialToScan` :125, `searchPathsForPlugins` :138, `getDefaultLocationsToSearch` :147, `requiresUnblockedMessageThreadDuringCreation` :150, and protected `createPluginInstance` :173.
- `juce::AudioPluginInstance` adds one own pure virtual, `fillInPluginDescription` (`juce_AudioPluginInstance.h:70`), plus all `juce::AudioProcessor` pure virtuals (`juce_AudioProcessor.h`): `getName` :109, `prepareToPlay` :139, `releaseResources` :145, `processBlock` :221, `getTailLengthSeconds` :856, `acceptsMidi` :864, `producesMidi` :872, `createEditor` :1027, `hasEditor` :1034, the five program methods :1131-1143, `getStateInformation` :1161, `setStateInformation` :1204. Parameters should be `juce::HostedAudioProcessorParameter` subclasses via `addHostedParameter`/`setHostedParameterTree` (:105-130).
- JUCE's own caveat, `juce_AudioPluginInstance.h:48-51` — "This class is not needed when writing plugins, and you should never need to derive your own sub-classes from it." A format implementer must derive it regardless (JUCE's VST3/LV2 formats do), but there is no stability guarantee attached.

### 4. Two concrete Tracktion gaps this route creates — both known, both small

- **Format identity is not persisted.** `ExternalPlugin::create` (:672-681) and `flushPluginStateToValueTree` (:1043-1049) write only `type, uniqueId, uid, filename, name, manufacturer` — not `pluginFormatName`. On reload `createIdentifierString` (:19-21, `pluginFormatName + "-" + name + hash`) can't match a CLAP KnownPluginList entry, and the extension-inference helper knows only `.vst3/.vst/.dll/audiounit:` (:899-905) with explicit retries for "VST3"/"VST"/"AudioUnit" (:916-926). Recovery still works via the `fileOrIdentifier` match (:848-851) and name scans (:933-941), i.e. by filename, not format identity. Fix: supply `EngineBehaviour::findDescriptionForFileOrID` — which exists for exactly this, `tracktion_EngineBehaviour.h:54-55`, "Gives an opportunity to load custom plugins for those that have been registered as custom formats but not added to the list."
- **Out-of-process scanning excludes custom formats twice over.** `CustomScanner::shouldUseSeparateProcessToScan` (`plugins/tracktion_PluginScanHelpers.h:321-331`) returns true only for names containing "AudioUnit", "VST" or "LADSPA"; and `PluginScanChildProcess`'s constructor calls only `addDefaultFormatsToManager` (:176-180), matching by `format->getName()` (:197-199), so the child cannot see a host-registered CLAP format. Sandboxed CLAP scanning requires patching that header or scanning CLAP outside the KnownPluginList scan.
- One benign special case to be aware of: `tracktion_ExternalPlugin.cpp:543` skips default-channel-config coercion for AU/VST3 only, so a CLAP would get `setDefaultChannelConfig` applied when no saved layout exists. And at :791-797 parameter IDs default to the parameter *index*, with only Cmajor opting into `getParameterID()`; the comment says "Don't broaden this to other formats… would orphan automation in existing edits" — a new format has no existing edits, so it is free to opt in, and should.

### 5. In-process vs out-of-process: scanning yes, hosting no

- **Out-of-process hosting does not exist in this stack.** JUCE: the only "Out-of-process" string in the audio stack is the AudioPluginHost's *scan-mode* combo box (`MainHostWindow.cpp:233`); there is no remote/proxy `AudioProcessor`; `juce::MemoryMappedFile` maps on-disk files and `InterprocessConnection` is a message-thread pipe — neither is usable in an audio callback. Tracktion: `ExternalPlugin` calls the instance directly (`processPluginBlock`, `tracktion_ExternalPlugin.h:256`); the only `ChildProcess` uses in the engine are the plugin scanner and an FFmpeg shell-out.
- **What building it would cost, read off Carla @ 97a9e074 (GPL-2.0-or-later — reference only, ruled out as a dependency):** a shared-memory audio pool (`BridgeAudioPool` with `float* data` and a `shm[64]` name, `CarlaBridgeUtils.hpp:230-247`); three ring buffers split by traffic class (:209-226); and per block, per plugin, a semaphore post plus a *blocking* timed wait inside the host's process callback — `waitForClient ("process", fProcWaitTime); if (fTimedOut) { … return false; }` (`CarlaPluginBridge.cpp:1881-1892`), where the wait is `jackbridge_sem_post` + `jackbridge_sem_timedwait` (`CarlaBridgeUtils.cpp:273-282`). Telling detail: the timeout is hard-coded to 1000 ms with the buffer-size-derived value commented out (`CarlaPluginBridge.cpp:2025-2026`). Carla also does *not* reparent bridged GUIs — it makes them transient for the host window (`XSetTransientForHint`, `CarlaPluginUI.cpp:439-445`), so out-of-process hosting costs the embedded-editor experience too.
- **Ardour does out-of-process *scanning* only** — separate `ardour-vst3-scanner`/`vst2-scanner`/`au-scanner` binaries (`libs/ardour/plugin_manager.cc:238-249`), with all plugin classes in-process.
- **First-party statements from the closed products** (implementations unverifiable): Bitwig — "In Bitwig Studio, plug-ins run in a separate process. This means that other parts of the program are protected if a plug-in misbehaves", and a five-mode spectrum where *Within Bitwig* "keeps the required computer resources to a minimum" and *Individually* "will require more computing resources" (bitwig.com support + user guide, retrieved 2026-08-07). REAPER — "Native bridging and firewalling: run 32-bit plug-ins in REAPER x64… protect against and recover from plug-in crashes" (reaper.fm/about.php). No vendor publishes a latency or CPU figure.
- **Out-of-process scanning, by contrast, is built and free.** Tracktion ships `PluginScanMasterProcess : juce::ChildProcessCoordinator` (:23), `PluginScanChildProcess : juce::ChildProcessWorker` (:175) and `CustomScanner : juce::KnownPluginList::CustomScanner` (:264) in `tracktion_PluginScanHelpers.h`, installed at `tracktion_PluginManager.cpp:79-86`, with the app-side entry point `PluginManager::startChildProcessPluginScan` (`tracktion_PluginManager.h:28`). Crash handling: `handleConnectionLost()` sets `crashed = true` (:129-132); on Windows the child wraps each scan in SEH `__try/__except` → `juce::Process::terminate()` (:236-250); the scanner relaunches once — "if there's a crash, give it a second chance with a fresh child process, in case the real culprit was whatever plugin preceded this one" (:294-295); failure to launch falls back to in-process scanning (:312).
- **It is off by default and Duet must turn it on:** `virtual bool canScanPluginsOutOfProcess() { return false; }` — `tracktion_EngineBehaviour.h:85`, gated through `PluginManager::usesSeparateProcessForScanning()` (`tracktion_PluginManager.cpp:411-416`).
- **What the isolation actually buys, and where it stops.** The child's work is exactly `format->findAllTypesForFile` (`tracktion_PluginScanHelpers.h:203`), so it protects load/instantiation and metadata query only — once a plugin is instantiated for playback it is an in-process `juce::AudioPluginInstance` and a crash takes the DAW with it. JUCE states the intent in the interface itself: `KnownPluginList::CustomScanner::findPluginTypesFor` — "@returns true if the plugin loaded, false if it crashed" (`juce_KnownPluginList.h:198-200`), with `false` auto-blacklisting the file (`juce_KnownPluginList.cpp:193-197`). Without a child process, JUCE's fallback is the dead-man's-pedal file, whose own doc concedes the cost: "even if there's a few dodgy plugins in your path, then a couple of rescans will still manage to find all the proper plugins" (`juce_PluginDirectoryScanner.h:58-68`) — i.e. a full app restart per crashing plugin.

### 6. GUI embedding: X11 XEmbed on Linux, HWND parenting on Windows, no Wayland on either side

- **JUCE 9 has no Wayland backend.** `juce_gui_basics/native/` contains `juce_Windowing_linux.cpp`, `juce_XWindowSystem_linux.*`, `juce_XSymbols_linux.*`, `juce_WindowUtils_linux.cpp`, `juce_DragAndDrop_linux.cpp` — no `*_wayland*` file anywhere in `modules/`. The peer is `LinuxComponentPeer` taking a `::Window parentToAddTo` (`juce_Windowing_linux.cpp:38-42`), gated on `isX11Available()` (:51). The three "wayland" hits in the whole tree are two XWayland *workarounds* (`DemoRunner/Source/Main.cpp:165`; `juce_WebBrowserComponent_linux.cpp:814-815` forcing `juce_gdk_set_allowed_backends("x11")`) and VST3 SDK headers. `docs/Linux Dependencies.md:42,73` lists X11 packages only. JUCE's latest roadmap post (Q3 2025) says only "we're now turning our attention to embedded platforms and Linux" — no Wayland commitment.
- **CLAP forbids Wayland embedding outright**, `include/clap/ext/gui.h:66-68` — `CLAP_WINDOW_API_WAYLAND` "uses physical size / embed is currently not supported, use floating windows". The `clap_window` union (:74-89) has cocoa/uikit/x11/win32 members and **no wayland member**.
- **VST3 embedding via JUCE is already solved and is a working model to copy for CLAP.** `VST3PluginWindow` is simultaneously the editor, the `IPlugFrame` and the Linux run loop (`juce_VST3PluginFormat.cpp:235-239`); it passes `defaultVST3WindowType` = `kPlatformTypeHWND` / `kPlatformTypeX11EmbedWindowID` (`juce_VST3Common.h:70-76`) into `view->attached ((void*) pluginHandle, defaultVST3WindowType)` (:483). Windows uses an `HWNDComponent`-based holder, Linux/BSD an `XEmbedComponent` configured `withWantsKeyboardFocus(true).withAllowForeignWidgetToResizeComponent(false).withIgnoreXembedMapped()` (:539-572). The SDK confirms the protocol: "The parent parameter in IPlugView::attached() is a X11 Window supporting XEmbed" (`iplugview.h:76-79`).
- **The Linux run-loop obligation is the part people forget, and it has a CLAP twin.** VST3: "On Linux the host has to provide this interface to the plug-in as there's no global event run loop defined as on other platforms" (`iplugview.h:261-278`), and JUCE implements `class RunLoop : public Linux::IRunLoop` (`juce_VST3PluginFormatImpl.h:411`), bridging fds via `LinuxEventLoop::registerFdCallback` (:473) and timers via `juce::Timer`. **CLAP requires Duet to write the equivalent by hand**: `clap_host_posix_fd_support` — "This extension let your plugin hook itself into the host select/poll/epoll/kqueue reactor" with a *level-triggered* `on_fd` (`posix-fd-support.h:5-7,24-45`) — and `clap_host_timer_support`, whose `register_timer` doc says "The host may adjust the period if it is under a certain threshold. 30 Hz should be allowed" (`timer-support.h:65-76`). Same primitives, different plumbing.
- **The CLAP embedding call sequence is fully specified**, `gui.h:19-33`: `is_api_supported` → `create` → `set_scale` → `can_resize` → `set_size`/`get_size` → `set_parent` → `show` → `destroy`. `gui.h:16-17` — "The Embedding protocol is by far the most common, supported by all hosts to date". Resize is bidirectional: plugin-initiated via `clap_host_gui->request_resize()` where "If the host returns false, the new size is rejected" (:35-39), drag-initiated via `adjust_size` → `set_size` (:41-45). Duet must also supply `resize_hints_changed`, `request_show`, `request_hide` and `closed(host, was_destroyed)` (:214-245).
- **The exact mapping is one line.** `juce::XEmbedComponent::getHostWindowID()` returns `unsigned long` — "Use this method to retrieve the host's window id when using the host initiated version of the XEmbedProtocol" (`juce_XEmbedComponent.h:176-179`) — and CLAP's `clap_xwnd` is `unsigned long` (`gui.h:77`). So `clap_window{ .api = CLAP_WINDOW_API_X11, .x11 = component.getHostWindowID() }` → `set_parent()`. On Windows, CLAP defines its embedding as `SetParent` (`gui.h:53`) and `juce::HWNDComponent` (`juce_HWNDComponent.h:41-53`) is the counterpart, with the parent HWND from `juce::Component::getWindowHandle()` (`juce_Component.h:2374-2378`).

### 7. Sidechain: free from Tracktion, but only if the wrapper declares a second bus

- **Tracktion's sidechain API is on the base `Plugin` class, so `ExternalPlugin` inherits it**: `canSidechain()` `tracktion_Plugin.h:365`, `getSidechainSourceNames` :386, `setSidechainSourceByName` :389, `guessSidechainRouting` :395, `makeConnection` :414, `sidechainSourceID` :554-555,620. `ExternalPlugin` does **not** override `canSidechain` — a grep finds it only in `tracktion_Plugin.cpp:238`, `tracktion_Plugin.h:365` and a test.
- **The detection test is pure channel counting**, `tracktion_Plugin.cpp:238-247`: `getChannelNames (&ins, &outs); return ins.size() > 2 || ins.size() > outs.size();` (and false if in a Rack). `ExternalPlugin::getChannelNames` (:1557-1591) reports `pi->getTotalNumInputChannels()`/`getTotalNumOutputChannels()`. **Therefore: the CLAP wrapper must expose the sidechain as a second JUCE input bus so total input channels exceed 2. Tracktion never asks whether a bus *is* a sidechain.**
- Routing is wire-based with a hard-coded convention: `guessSidechainRouting` maps `(0→0),(1→0),(2→1),(3→1)` for a stereo plugin (:295-331) — source channels 0/1 are the plugin's own track, ≥2 are the sidechain track, confirmed by `tracktion_EditNodeBuilder.cpp:1221-1223` ("Wires always use two source channels for the plugin's track"). Wires persist as `SIDECHAINCONNECTIONS`/`SIDECHAINCONNECTION` ValueTree children with `srcChan`/`dstChan` (:191-214). The graph builds the sidechain leg as a `ReturnNode` on a bus id hashed from the source `EditItemID`, remapped and summed with the direct input (`tracktion_EditNodeBuilder.cpp:1208-1258`), fed by a `SendNode` on the source track (:1641-1642).
- **VST3's sidechain is a bus *type* — and JUCE throws that information away when hosting.** The SDK has `BusTypes { kMain = 0, kAux }` with "kAux ///< auxiliary bus (sidechain)" (`ivstcomponent.h:82-86`) and requires "The kMain busses have to place before any others kAux busses" (:57). JUCE's host-side `getBusProperties` (`juce_VST3PluginFormatImpl.h:3229-3258`) reads `getBusInfo` but **never reads `info.busType`** — an exhaustive `grep -rn kAux modules/` hits only the plugin-side wrapper and the SDK. A hosted sidechain is therefore just "input bus index ≥ 1", carrying its VST3 name and `kDefaultActive` flag. Note a scanning consequence: a sidechain bus that is not default-active contributes 0 to `PluginDescription::numInputChannels` (:294-313, :1596-1609).
- **CLAP has no first-class sidechain concept at all.** `grep -rniE "side.?chain"` over the entire clap repo @ a47f6bad — headers, `conventions/`, `src/`, README, ChangeLog — returns **zero matches**. The only structural distinction is `CLAP_AUDIO_PORT_IS_MAIN` — "There can be only one main input and main output. Main port must be at index 0" (`audio-ports.h:24-28`). `port_type` values are channel *layouts* (`CLAP_PORT_MONO`/`STEREO`/`SURROUND`/`AMBISONIC`), not roles, and neither `audio-ports-config.h` nor `configurable-audio-ports.h` carries a role field. So Duet's host must identify a CLAP sidechain as "input port index ≥ 1 lacking `CLAP_AUDIO_PORT_IS_MAIN`" and label it by `port_info.name` — convention, and one not even written down in the CLAP repo.
- **Pleasing symmetry**: both formats reduce to "non-main input bus/port", which is exactly what Tracktion's channel-count test wants. The wrapper does not have to invent a sidechain abstraction; it has to map ports to buses faithfully.

### 8. State: free from Tracktion, with one stream contract to honour

- **Tracktion persists plugin state as base64 in the Edit.** `ExternalPlugin::flushPluginStateToValueTree` (`tracktion_ExternalPlugin.cpp:1036-1073`), on the message thread with `pi->suspendProcessing(true)` around it, calls `pi->getStateInformation (chunk)` and `state.setProperty (IDs::state, chunk.toBase64Encoding(), um)` (:1067), removing the property when empty (:1069). Restore mirrors it: `chunk.fromBase64Encoding(s)` then `callBlockingCatching([&]{ pi->setStateInformation(...); })` (:1123-1126), called during instance creation at :1919. Bus layout persists *separately* as a raw `MemoryBlock` under `IDs::layout` (:1075-1091) — so a sidechain bus's enabled state survives reload through the layout property, not the plugin's own chunk.
- CLAP's side is small: `clap_plugin_state { save, load }`, both `[main-thread]` (`state.h:24-34`), plus the host's `clap_host_state::mark_dirty` — "Tell the host that the plugin state has changed and should be saved again. If a parameter value changes, then it is implicit that the state is dirty" (:36-41).
- **The one real trap is the stream contract**, `stream.h:8-16` — "the host may limit the number of bytes that can be read or written at a time… You need to use a loop to ensure that you read or write the entirety of your state. Don't forget to also consider the negative return values for the end of file and IO error codes." `read` returns bytes read, 0 = EOF, -1 = error; `write` returns bytes written, -1 = error (:22-34). Duet's `MemoryBlock`-backed `clap_ostream`/`clap_istream` must implement the loop correctly on both sides.
- For contrast, JUCE's VST3 state is heavier — an XML `"VST3PluginState"` element with base64 `IComponent` and `IEditController` children (`juce_VST3PluginFormatImpl.h:2802-2819`), restored component-then-controller with a parameter reset in between (:2822-2864), all under a `MessageManagerLock` because "The VST3 plugin format requires that get/set state calls are made from the message thread".

### 9. The one existing CLAP-as-AudioPluginFormat implementation, assessed honestly

- `github.com/jatinchowdhury18/juce_clap_hosting` exports a `CLAPPluginFormat : juce::AudioPluginFormat` intended for `pluginFormatManager.addFormat (new juce::CLAPPluginFormat);`. **MIT** ("This repository is licensed under the MIT license").
- **Dead**: `created_at 2022-10-06T18:07:04Z`, `pushed_at 2022-10-06T18:07:25Z`, 13 stars, latest commit `aa8a8123` 2022-10-06. It predates JUCE 8 and 9 entirely.
- **Alpha, by the author's own words**: "this software should be considered super-alpha!" Its TODO leaves unimplemented `CLAP_PATH` scanning, audio-port config validation, **MIDI support**, `clapParamsClear`/`clapParamsFlush`, process/restart requests, and the **state, GUI, latency, thread-check, render and tail extensions**. Tested with stereo plugins only. For a milestone that must host CLAP *instruments* with persisted state and native GUIs, this is a reference implementation, not a dependency.
- Everything else in the ecosystem points the other way: `clap-juce-extensions` builds a CLAP plugin *from* a JUCE project; `clap-wrapper` wraps CLAP plugins *into* other environments. Neither hosts.

## Unresolved

- **Whether Waveform hosts CLAP.** No primary source establishes it, and CLAP's own host list omits Waveform. I also could not find a tracktion.com page enumerating Waveform's formats with a quotable sentence, so I cannot cite a positive denial either. Settling it would need a Waveform install's format list or a first-party statement. Low stakes: the open engine has no CLAP either way, and Tracktion's own Cmajor format proves the seam works regardless.
- **Whether JUCE's `develop` branch (which tracktion_engine pins) differs from the `master` @ 7dda739b that was read.** CLAP's total absence from master makes a CLAP format on develop very unlikely, but develop was not checked directly.
- **Whether JUCE's hosted VST3 path exposes `busType` anywhere at all.** Verified by exhaustive grep for `kAux` that it does not, but `juce_VST3PluginFormatImpl.h` was not read end-to-end, so a path that reads `info.busType` into a differently-named local cannot be strictly excluded. The only bus-property construction path discards it.
- **Whether the Tracktion sidechain leg is latency-compensated.** Only the construction of `SendNode`/`ReturnNode` was read, not the runtime behaviour. Worth checking against a real sidechain compressor during implementation.
- **Any first-party measurement of out-of-process hosting cost.** None exists in any reachable source. Bitwig's user guide is qualitative only. The structural cost (a blocking semaphore round-trip per plugin per block) is readable from Carla's code but is not a benchmark.
- **Nothing here was compiled or run.** Every claim is source reading at the stated commits. The seam's real behaviour is exactly what the follow-on prototype node exists to test.
