## Question

With JUCE 9 chosen as the application foundation (node 1hn16k), does the engine layer — playback, recording, mixing, automation, tempo, render — get written from scratch on JUCE's audio classes, or adopted from an existing engine (Tracktion Engine being the candidate JUCE keeps on the table)?

## Answer

**Adopt Tracktion Engine.** Three findings decide it, and the third is the one that mattered most to this project specifically.

1. **It covers milestone one almost exactly.** Every item in node kimula's list has a class that owns it: the recording lifecycle with record-arm, input routing and monitor modes; plugin delay compensation; submix folder tracks for arbitrary group buses; aux send/return; sidechain routing with a first-class `canSidechain`/wire API and a compressor with a sidechain trigger; EQ, compressor and reverb; bezier automation curves; a tempo sequence; a click generator; a renderer that writes WAV; and time-stretching with a bundled MIT backend. The gap list is short and known.

2. **The scratch path is much larger than "JUCE has audio classes" suggests.** JUCE 9 gives real machinery — device management, format readers/writers, background disk streaming both directions, lock-free primitives, and (a genuine surprise, verified in source against the common belief) automatic plugin delay compensation inside `AudioProcessorGraph`. But it ships **no mixer semantics whatsoever** — no fader, pan, send, bus or meter node exists; the only built-in node type is device I/O — and no time-stretching, no metronome, no automation-curve engine, no tempo/musical-time playhead, no session document model, no streaming sampler, and no offline render driver. Every one of those is milestone-one work, and none of it is what makes this DAW different from any other.

3. **Tracktion Engine's data model is close to purpose-built for this project's AI seam.** This was the stated risk in the brief — "an adopted engine's model may fight that" — and the research says the opposite. The roadmap's AI data strategy makes the project data model the entire AI surface: every Collaborator tool reads from it, and every Collaborator edit enters through the same edit vocabulary the human uses, sharing undo. Tracktion Engine's `Edit` **is** a `juce::ValueTree`: traversable, mutable through a documented headless API, observable through ValueTree listeners, serialisable as XML, with one `UndoManager` per Edit that the engine's own tests drive programmatically, and an audio graph that rebuilds itself automatically from model changes — including on undo, because undo is just another tree mutation. A scratch build would spend months arriving at a weaker version of this.

The costs accepted, in order of how much they should worry us:

- **The commercial edition now costs a permanent subscription, not a purchase.** This is the real price of the decision and it belongs to node a3p83b. Nothing changes today — the open-source project takes the GPLv3 arm for free — but a closed edition later needs a Tracktion Engine subscription *maintained for as long as the binary is distributed*, **on top of** a JUCE licence, with a revenue limit defined as organisation-wide gross revenue including funding. JUCE's commercial route is a perpetual purchase for a version; Tracktion's is rent, and stopping it ends the right to keep distributing what you already shipped.
- **No UI at all**, stated by the maintainers. This is not a cost of adoption though — the UI is hand-written on either path.
- **You cannot upstream fixes**: the project does not accept third-party pull requests, and bug reports go to a forum rather than the issue tracker.
- **`tracktion_graph` self-describes as experimental** with an unstable API, and the last tag is 15 months old while `develop` (the default branch, ~1.5 minor versions ahead) is where the live work happens. Pinning a commit, not a tag, is the practical consequence.

**The mitigation that makes this reversible enough to accept:** keep Duet's own edit vocabulary (node hll1mo) and the Collaborator's tool vocabulary as a seam in front of the engine, rather than letting `tracktion::engine` types leak through the application. The seam is worth building for the AI design regardless — it is where the Suggestion model and shared undo live — and it doubles as the thing that keeps a future engine swap from being a rewrite.

### The data model — why this is the deciding axis

- **`Edit` is the document and it is a ValueTree.** `juce::ValueTree state { IDs::EDIT };  ///< The ValueTree of the Edit state.` — `model/edit/tracktion_Edit.h:892` (public). Edits are constructed from a tree via `Options { Engine&, juce::ValueTree editState, … }` (:107–110).
- Documented hierarchy (class comment, `tracktion_Edit.h:38–61`): Edit → TempoSequence → TimeSigSetting/TempoSetting; PitchSequence; TrackList → Track (Arranger, Marker, Tempo, Chord, Audio, Folder, Automation) → Clip (WaveAudio, Midi, Step, Edit), PluginList → Plugin → AutomatableParameter → AutomationCurve; juce::UndoManager.
- **Every model object is a thin wrapper over its own tree node**, each exposing a public `state`: `Track` (`model/tracks/tracktion_Track.h:380`), `Clip` (`model/clips/tracktion_Clip.h:449`), `Plugin` (`plugins/tracktion_Plugin.h:604`), `MidiList` (`midi/tracktion_MidiList.h:188`), `MidiNote` (`midi/tracktion_MidiNote.h:78`). Objects mirror the tree through `ValueTreeObjectList` (`utilities/tracktion_ValueTreeUtilities.h:89`). Stable identity is `EditItemID` with `findTrackForID`/`findClipForID` (`model/edit/tracktion_EditUtilities.h:72,130`).
- **On disk it is that tree as XML.** `edit.flushState(); … if (auto xml = edit.state.createXml()) ok = xml->writeTo (file);` — `model/edit/tracktion_EditFileOperations.cpp:172–202`. A binary ValueTree variant exists for temp/autosave; loading accepts either, XML first (:602–621). Extensions: `*.tracktionedit;*.trkedit` (`project/tracktion_FolderBasedProject.cpp:92`).
- **One UndoManager per Edit, public**, with `getUndoManager()`, `undo()`, `redo()`, default 30 levels — `tracktion_Edit.h:335–365`, member at :940. Mutations are ValueTree writes passed that manager (`tracktion_Edit.cpp:1905, 1986–1987, 2203`), and scalar properties bind via `CachedValue::referTo (state, IDs::…, um, default)`.
- **Undo works end to end on high-level operations**, proven by the engine's own test: `beginNewTransaction(); splitClips ({clip}, 2_tp); CHECK_EQ (…getClips().size(), 2); undo(); CHECK_EQ (…getClips().size(), 1);` — `model/automation/tracktion_AutomationCurveList.test.cpp:697–730`.
- **Two undo caveats that bear directly on the AI seam.** (a) Transactions are grouped by a **350 ms timer** tied to mouse-up (`Edit::UndoTransactionTimer`, `tracktion_Edit.cpp:20–58`), so a scripted or Collaborator-driven caller must call `beginNewTransaction()` explicitly to control boundaries — which is what the engine's own tests do. (b) Undo is **opt-in per call**: every mutating API takes a `juce::UndoManager*` and callers may pass `nullptr`; live plugin-parameter setting does exactly that (`model/automation/tracktion_AutomatableParameter.cpp:888`), so it is not undoable, though writing the underlying property is.
- **Observability**: `juce::ValueTree::Listener` on any object's `state` is the primary mechanism — the engine's own `Edit::TreeWatcher` is one (`tracktion_Edit.cpp:89`). Adapters provided: `ValueTreeAllEventListener`, `LambdaValueTreeAllEventListener`, `ValueTreePropertyChangedListener` (`utilities/tracktion_ValueTreeUtilities.h:360–470`). A second layer, `Selectable`/`SelectableListener`, is implemented by Edit, Track, Clip and Plugin (`selection/tracktion_Selectable.h:19–81`), plus per-object listeners such as `AutomatableParameter::Listener`.
- **The full edit vocabulary is available headlessly.** Tracks: `insertNewAudioTrack`, `insertNewFolderTrack`, `insertNewAutomationTrack`, `insertTrack` (`tracktion_Edit.h:398–411`) — the `SelectionManager*` is optional and `nullptr` in headless use. Clips: `insertNewClip`, `insertWaveClip`, `insertMIDIClip`, `insertClipWithState` (`model/clips/tracktion_ClipOwner.h:87–117`); move/trim via `setPosition`/`setStart`/`setLength`/`setOffset`/`trimAwayOverlap`/`moveTo` (`tracktion_Clip.h:265–300`); `splitClips`. MIDI: `MidiClip::getSequence()` → `addNote`/`removeNote`/`addControllerEvent`/`rescale`/`importMidiSequence`. Automation: `AutomatableParameter::getCurve()` → `addPoint`/`setPointValue`/`removePoints`. Tempo/key: `TempoSequence::insertTempo`, `PitchSequence::insertPitch`. Read-side traversal: `getAllTracks`, `getAudioTracks`, `getAllPlugins`, `Edit::visitAllTracksRecursive`.
- **The audio graph rebuilds itself from the model.** "Use this to tell the play engine to rebuild the audio graph if the toplogy has changed. You shouldn't normally need to use this as it's called automatically as track/clips/plugins etc. are added/removed/changed." — `Edit::restartPlayback()` doc, `tracktion_Edit.h:366–370`. `TreeWatcher` triggers it on relevant tree changes, coalesced through a 1 ms timer into `TransportControl::editHasChanged()` → `createNodeForEdit` (`playback/graph/tracktion_EditNodeBuilder.h:64`). **Because undo is itself a tree mutation, undo rebuilds the graph too** — the property that makes shared human/AI undo tractable.
- **Model and graph are separate modules** with a one-way builder — `tracktion_graph`, "Classes for creating and processing audio graphs". Its own header warns: "tracktion_graph is an experimental module. It is currently in an early stage of development so the API or functionality it contains is in no way stable."
- **Custom application data has a demonstrated home**: the engine's own example stores an `EDITVIEWSTATE` child tree under `edit.state` with properties bound to the Edit's UndoManager (`examples/common/Components.h:14,43–60`), and it persists because saving serialises `edit.state` wholesale. There is also a first-party hook acknowledging that applications keep their own trees referencing engine IDs: `static std::function<void (juce::ValueTree&, const juce::Identifier&, const std::map<juce::String, EditItemID>&, juce::UndoManager*)> applyNewIDsToExternalValueTree;` (`model/edit/tracktion_EditItem.h:70–77`). Further seams via `EngineBehaviour`: `saveCustomPluginProperties`, `newClipAdded`, `createCustomPlugin`.

### The scratch path on bare JUCE 9 — what it would actually cost

All from a clone at tag `9.0.0`.

- **Provided**: `AudioDeviceManager` (device selection, callbacks, MIDI aggregation); `AudioFormat`/`Reader`/`Writer` with WAV, AIFF, FLAC, Ogg, MP3-decode, LAME-encode, CoreAudio, WMA; `BufferingAudioReader`/`BufferingAudioSource`/`AudioTransportSource` for read-ahead playback; `AudioFormatWriter::ThreadedWriter` — "Provides a FIFO for an AudioFormatWriter, allowing you to push incoming data into a buffer which will be flushed to disk by a background thread." Device latency is *reported* (`getInputLatencyInSamples`/`getOutputLatencyInSamples`) but no JUCE class offsets recorded takes by it.
- **Correction to a widely held belief: `AudioProcessorGraph` DOES implement automatic audio plugin delay compensation.** `getInputLatencyForNode()` takes the max accumulated delay over source nodes; `findBufferForInputAudioChannel()` pads shorter paths — `const auto needsDelay = nodeDelay < maxLatency;` then `sequence.addDelayChannelOp (bufIndex, maxLatency - nodeDelay);`; per-node accumulation at `thisNodeLatency = maxInputLatency + processor.getLatencySamples()`; the graph reports total latency upward via `setLatencySamples`. Its own unit test asserts it ("rebuilding the graph recalculates overall latency"). — `modules/juce_audio_processors_headless/processors/juce_AudioProcessorGraph.cpp`. Note the class doc comment never claims PDC; the evidence is the code and its test, not prose.
- **Graph limitations**: MIDI is **not** delay-compensated (the MIDI buffer path contains no delay op at all), and feedback loops are **silently broken rather than rejected** — `canConnect()` performs no cycle check, and at build time a cycle resolves to `readOnlyEmptyBufferIndex` with the comment "if not found, this is probably a feedback loop". Graph rebuilds happen on the main thread with a wait-free swap onto the audio thread (`RenderSequenceExchange`).
- **Absent, verified by searching the whole module tree** — no mixer semantics of any kind (the only built-in node type is `AudioGraphIOProcessor`; there is no gain, pan, send, bus or meter node, so faders, pans, group buses and post-fader sends are all `AudioProcessor` subclasses you write); no time-stretch or pitch-shift (matches are only vendored AAX/VST3/LV2/oboe SDK headers and ARA plumbing); no metronome; no automation-curve engine (JUCE has a *parameter* model — `AudioProcessorParameter`, `AudioProcessorValueTreeState`, `SmoothedValue` — but breakpoint storage, interpolation and sample-accurate curve playback are yours); no tempo/musical-time timeline (`AudioPlayHead` is an interface for a host to implement — every implementation in the tree is a plugin-client wrapper relaying someone else's position); no session document model (only generic `ValueTree`/`UndoManager` infrastructure); no streaming sampler ("This is a pretty basic sampler, and just attempts to load the whole audio stream into memory."); no offline render driver (`setNonRealtime` and `writeFromAudioSource` are hooks, but the bounce loop — advance playhead, service automation, pump graph, feed writer — is yours).
- **Provided for real-time safety**: `AbstractFifo` ("Encapsulates the logic required to implement a lock-free FIFO… single-reader, single-writer"), `SingleThreadedAbstractFifo`, `FixedSizeFunction`, `SpinLock`, `Thread::RealtimeOptions` (with `withApproximateAudioProcessingTime`), `AudioBuffer`, `FloatVectorOperations`, `AudioWorkgroup`, `SmoothedValue`, `MidiBuffer`, `MidiMessageSequence`, `MidiFile`, `Synthesiser`, `MPESynthesiser`, and `MidiMessageCollector` — "Collects incoming realtime MIDI messages and turns them into blocks suitable for processing by a block-based audio callback." Also `AudioThumbnail`/`AudioThumbnailCache` for waveform display and `AudioProcessorPlayer` to run a graph on a device.
- **JUCE does ship resampling** (`ResamplingAudioSource`, `Interpolators` — Lagrange, Catmull-Rom, windowed-sinc, linear), so libsamplerate is optional rather than mandatory on either path.
- **Licences of the gap-filling libraries** (relevant to both paths, and to which time-stretch backend gets enabled): **Signalsmith Stretch — MIT** (`LICENSE.txt`, github.com/Signalsmith-Audio/signalsmith-stretch, "MIT License / Copyright (c) 2022 Geraint Luff / Signalsmith Audio Ltd."), header-only C++11, and the only copyleft-free option. SoundTouch — **LGPL v2.1** (`COPYING.TXT`, codeberg.org/soundtouch/soundtouch). Rubber Band — **GPLv2 with a paid commercial alternative** ("If you want to distribute it in a proprietary commercial application, you need to buy a licence." — breakfastquay.com/rubberband/). libsamplerate — BSD-2-Clause. **Rubber Band's GPLv2 is not compatible with AGPLv3 JUCE without going commercial on both**, which settles the backend question in Signalsmith's favour independently.

## Consequences for the rest of the roadmap

- **ddp1qt** (walking skeleton) — the skeleton now builds JUCE 9 + Tracktion Engine `develop` together, on top of its existing mandate to prove the Linux rendering path. Two additions worth proving there: that the C++20 requirement and the pre-9 vendored JUCE submodule cause no friction when pointed at JUCE 9 (CI says green, our build is the real test), and that `JUCE_ENABLE_SIGNALSMITH_STRETCH` (or its actual flag name) gives working time-stretch.
- **psmj4y** (toolchain) — floor rises to **C++20** (Tracktion's requirement, above JUCE's C++17). Dependency management must pin Tracktion Engine to a **commit on `develop`**, not a tag, since the last tag is 15 months stale. CMake floor `3.15...3.20`.
- **a3p83b** (licence + CLA) — materially changed. A commercial edition now needs a Tracktion Engine subscription maintained for the whole distribution period *on top of* a JUCE licence, and the revenue limit is organisation-wide gross revenue including funding. Noted on that issue.
- **86t5lu** (foundation spec) — the "project data model" gap in its brief is now largely answered: the model is Tracktion's `Edit` ValueTree, with Duet's own data as child trees under `edit.state`.
- **hvv3nn** (plugin hosting) — Tracktion routes VST3 through JUCE's format manager (`addDefaultFormatsToManager`), so the CLAP host still has to be hand-written and now also has to present itself to Tracktion as a plugin type. That is a new wrinkle for that node.

## Unresolved

- **Whether perpetual (non-subscription) Tracktion Engine licences exist, and at what price.** The FAQ implies they do — it says a distributor of third-party-contributed code "is legally obliged to ensure that the corresponding licences are perpetal, rather than subscription, Tracktion Engine licences" — but no perpetual SKU appears on the pricing page and the EULA defines only subscription and free tiers. Tried: pricing page, full EULA, tracktion.com developer page. Requires contacting sales. **This matters to a3p83b**, because it is the difference between rent and a purchase.
- **Whether the organisation-wide revenue limit reaches an individual licensee's unrelated income** (e.g. salary). The EULA language is broad ("all monies collected, including through funding… without offsets of any kind") and the FAQ says the limit "is that of the whole organisation or individual that owns the Tracktion Engine licence", but no worked example exists. Only bites if a paid tier is ever taken; the GPL route has no limit.
- **Whether Tracktion officially supports JUCE 9**, as opposed to "the nightly CI build against JUCE develop passes". No statement in README, CHANGELIST, BREAKING-CHANGES or CMakeLists (grep for "JUCE 9"/"JUCE9" → 0 hits), and the vendored submodule is still pre-9. The JUCE Forum was not searched for a staff statement.
- **Whether custom properties written directly onto engine-owned nodes** (a `TRACK` or `MIDICLIP` tree) survive a save→load round trip untouched. Save and load are verbatim `createXml`/`fromXml` with no filtering found, but no test or doc asserts preservation and `updateLegacyEdit()` rewrites old formats. Only the child-tree-under-`edit.state` pattern is demonstrated by primary source. **Empirically testable in ddp1qt or the persistence node.**
- **Whether the graph's delay lines compose across nested `AudioProcessorGraph`s.** The outer graph reads the inner's `getLatencySamples()`, so it should, but no unit test covers nesting. Moot unless the scratch path is revisited.
- **Explicit pre/post-fader semantics for aux sends in Tracktion.** No such flag exists in the module (grep for "post fader"/"pre fader" → 0 hits); pre/post is expressed by the send plugin's position relative to `VolumeAndPanPlugin` in the track's plugin list. Milestone one needs post-fader only (kimula), so ordering suffices, but this is an inference from architecture, not a maintainer statement.
- **Per-track loudness as a model-readable value** — `playback/tracktion_LevelMeasurer.h` and `SharedLevelMeasurer` are runtime meters; no offline deterministic loudness analysis API was verified. This bears on the Collaborator's tool vocabulary, where measured loudness is a named requirement.
